## What was built

- **`supabase/migrations/003_share_lookup_by_code.sql`** (new).
  - Adds `public.storybook_by_share_code(code text)`. It is `LANGUAGE sql STABLE STRICT SECURITY DEFINER SET
    search_path = public`. It returns the one storybook whose `shared_links.share_code = code` (exact equality on the
    UNIQUE column) and whose `is_public = true`.
  - It returns only the Reader's columns: `id, title, author, genre, age_range, page_count, description,
    cover_image_url, created_at, ssync_data`. It never returns `user_id`, `is_public`, `is_premium`, the counters or
    `updated_at`.
  - `REVOKE ALL … FROM PUBLIC`, then `GRANT EXECUTE … TO anon, authenticated`.
  - Drops "Anyone reads shared links", "Anyone reads public storybooks" and "Public media readable". Nothing in `src/`
    reads `page_media`, because a tape's pictures and narration travel inside `storybooks.ssync_data`, which the
    function returns.
  - Every owner policy stays untouched.
  - It contains no `UPDATE`, `DELETE`, `INSERT`, `TRUNCATE`, `DROP TABLE`/`COLUMN`/`FUNCTION` or `ALTER TABLE`, not
    even in comments.
  - It is idempotent: `CREATE OR REPLACE`, `DROP POLICY IF EXISTS`, and grants. It ends with
    `NOTIFY pgrst, 'reload schema'`, so PostgREST sees the function at once.
  - The header says why the migration exists, what it changes, that the app works before and after (the PGRST202
    fallback), and that Jon applies it to production and agents do not.
- **`src/lib/supabase.ts`**
  - `getStorybookByShareCode(code, client = supabase)` calls `client.rpc("storybook_by_share_code", { code })` first.
  - Only on "function not found" (`PGRST202` from PostgREST, `42883` from Postgres) does it fall back to
    `storybookByShareCodeBefore003`. That is today's two-step exact-match select: link by `.eq("share_code", code)`,
    then the one story by `.eq("id", …)`. The fallback now uses `.maybeSingle()` and the Reader's column list instead
    of `select("*")`, and it throws its own errors instead of swallowing them.
  - Any other RPC error is thrown untouched.
  - New exports: `ShareLookupClient` (`Pick<client, "rpc" | "from">`, the stub seam) and `SharedStorybookRow`.
- **`src/lib/cloud-storage.ts`**
  - New `resolveShareCode(code, client = supabase)`, the cloud half of a share link. A string that is not lowercase hex
    (`/^[0-9a-f]+$/`, the only alphabet any code was ever minted in) resolves to `null` without a request.
  - A cloud failure becomes a `CloudError` through the module's existing `fromSupabase` ("Opening the tape").
  - The row maps through the existing `fromRow`, with `is_public: true`: a link only ever opens a published story.
  - `getSharedBook` calls it on the cloud path. The device path is unchanged and still accepts raw story ids.
  - There is no length check, so 16-hex codes from before T02 still resolve.
- **`PRIVACY.md`** rule 4 gets one sentence: "The app opens a shared story only by looking up its exact share code,
  which returns that one story and nothing else, and it never asks the cloud for a list of share codes or stories."
  - The "What 'public' means" paragraph said `is_public` "is the single condition the storage read policy checks".
    After 003 that policy is gone, so it now reads "It is what the cloud checks before it lets anyone but you open the
    story". That is true both before and after 003. It is a minimal edit inside rule 4 that keeps the doc true.
- **`tests/share-lookup.spec.ts`** (new): 29 Node-side tests (see below).
- **`docs/vision/evidence/T02b-migration-check.sh`** (new evidence script). It runs 001 → 002 → 003 on a throwaway
  Postgres with the Supabase roles and `auth.uid()` shimmed, and checks what anon and signed-in users can read before
  and after. It is not part of the suite (CI has no Postgres).

## Deviations and why

1. **The static test reads "without an owner filter" as "not narrowed to one row".** The ticket asks for a static
   check that no `from("shared_links").select(` without an owner filter remains. It also requires the pre-003 fallback,
   which reads `shared_links` by code and not by owner. So the check allows a `shared_links` read only when it names
   one exact code (`.eq("share_code", code)`) and asks for one row. `storybooks` reads must be the owner's (`user_id`)
   or the one id a link names. Neither can list.
2. **The function also requires `is_public = true`.** The ticket does not ask for this. It keeps today's semantics
   exactly: anon could only ever read published stories. So 003 narrows what a link holder can read and never widens
   it. A link to an unpublished story (which the app never makes) opens nothing.
3. **`STRICT` and `REVOKE … FROM PUBLIC` were added.** STRICT makes "NULL → nothing" structural. The revoke removes
   Postgres's implicit PUBLIC execute grant, so only the grants the ticket names apply (Supabase's default privileges
   still give `service_role` access).
4. **The fallback uses `.maybeSingle()`, and the Reader's columns instead of `select("*")`.** The result is the same
   for the app: one row or null. It no longer pulls `user_id` or the counters, and its errors are reported rather
   than swallowed. `tape-source.ts` still turns any failure into "try this device's library", so what a reader sees
   is unchanged.
5. **PRIVACY.md:** besides the one sentence, one phrase in the same rule ("the single condition the storage read
   policy checks") was reworded. Once 003 drops that policy, the old phrase would be false.
6. **The non-hex guard covers only the cloud path.** The device path still accepts a raw story id, as before, because
   older builds handed the id out as the code.
