## What was built

The protocol half of T04, spec first (HANDOFF §5). The order was spec, then schema, then code.

- **`docs/format-spec.md` §7**: a new §7.1, "`voiceConsent[]` — consent travels in the tape". It states:
  - one record per recorded voice;
  - the meaning of each field;
  - that `date` is `YYYY-MM-DD`, that readers MUST accept a timestamp and that validators SHOULD warn;
  - why the schema adds no `pattern`;
  - the example record `{ "voice": "Ada, age 4 — with Dad", "grantedBy": "parent/guardian", "date": "2026-10-19" }`;
  - the three WARN lines the reference validator prints.

  No other section changed.
- **`public/protocol/v2.schema.json`**: the `signature.voiceConsent` array has a description ("One record per
  recorded voice on the tape."). In its items:
  - `voice` has a description (whose voice, as credited);
  - `grantedBy` has a description (who consented) and `examples: ["parent/guardian", "self"]`;
  - `date` has a description (calendar date of consent, `YYYY-MM-DD`; validators warn on timestamps).

  `format: "date"` and `required: ["voice", "grantedBy"]` are unchanged, and no `pattern` was added.
- **`src/lib/storysync/manifest.ts`**:
  - `ValidationResult` gains `warnings: string[]`, which is always present.
  - `ok` is still `errors.length === 0`.
  - A private `consentWarnings()` adds the per-record date warnings and the manifest-level "SHOULD carry one"
    warning.
  - The `SsyncSignature.voiceConsent` TSDoc now carries the date rule, the `grantedBy` convention and the
    one-record-per-voice rule. The types are not narrowed.
  - `packStorysync` and `unpackStorysync` are untouched. They throw only on `!ok`, so a warning cannot block
    them.
- **`tests/storysync-roundtrip.spec.ts`**: a new `describe("consent (v2.1 draft)")` with 10 Node-side tests.
  The seven tests the ticket names are there, plus three more:
  - 3b: several records, each warned by its own index;
  - 4 also covers an empty array;
  - 6b: the s08 FAIL line is pinned verbatim and stays an error.

  Two `node:` imports and the `tests/fixtures/tapes` import were added at the top. The existing tests were not
  touched.

The product's behaviour does not change. `Studio.tsx` reads only `validation.ok` / `validation.errors`, and T04b
fixes the writer.

## Deviations from the reference, and why

- **The FAIL line's framing.** s08 prints ``FAIL a hand-edited copy: pages[2].text.audioUrl 'assets/narration-3.webm' …``,
  with single quotes and a "a hand-edited copy:" prefix. The validator's error string stays exactly as it is
  today: no prefix, and double quotes. The ticket requires that ("The existing errors are unchanged, including
  the s08 FAIL wording …" quotes it with double quotes). The prefix is the narration of the /protocol
  validator block, and T23 owns that rendering.
- **The PASS lines** ("version 2.0 · metadata.title · 5 pages", "every assets/ path in the manifest exists")
  are not validator output. `validateManifest` returns only errors and warnings. The PASS summary is
  presentation for T23b. The evidence image does not invent them.
- **Evidence uses the Rivera fixture** in `docs/` and `tests/` only. The product code and the spec example use
  original names ("Ada", "Grandpa Theo").

## Decision log entry

**2026-10-25 · T04a · The validator warns; consent dates are calendar dates; one consent record per voice.**

- `validateManifest` returns `warnings: string[]` alongside `errors`. A warning is drift from the v2.1 draft that
  still opens and plays. It never makes `ok` false, never makes `packStorysync` or `unpackStorysync` throw, and
  never blocks a publish. Errors keep their exact wording.
- `signature.voiceConsent[].date` is a calendar date, `YYYY-MM-DD`: the consenting device's local date. Readers
  MUST accept the full ISO timestamps older tapes carry, and validators SHOULD warn:
  - `signature.voiceConsent[i].date is a full timestamp; the v2.1 draft asks for a date`
  - `signature.voiceConsent[i].date "<value>" is not a calendar date (YYYY-MM-DD)`

  The schema keeps `format: "date"` and adds no `pattern`, so the rule never becomes a schema failure.
- There is one `voiceConsent` record per recorded voice. `grantedBy` is conventionally `"parent/guardian"` or
  `"self"` (free text allowed; there are schema `examples`, not an enum). A tape with a recorded voice and no
  record warns `a recorded voice is on this tape but signature.voiceConsent is empty; the v2.1 draft says it
  SHOULD carry one`.
