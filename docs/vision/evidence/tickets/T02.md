  before October 2026 used 64-bit codes". That was false: this change is not committed or deployed yet, so every cloud
  link made from 1 October until it deploys still gets the 64-bit column default. The sentence now uses the ticket's
  wording, tied to the change: "Cloud links made before share codes became 128-bit used 64-bit codes; they keep working
  until the story is deleted, and every new link is 128-bit." The evidence notes and the decision-log entry below use
  the same wording. No test asserts the date, so no test changed for this.
- **`shareBook`'s device path catches only `ShareCodeError`** (polish 1), like the cloud path:
  `catch (err) { if (err instanceof ShareCodeError) throw new CloudError("unknown", UNSAFE_LINK); throw err; }`.
  - Narrowing the catch alone made one case worse. A `getRandomValues` that exists but throws (a broken polyfill, a
    locked-down runtime) escaped `shareBook` as a raw `TypeError`. That broke the module's rule 1 that every throw is a
    `CloudError`, and it dropped the honest sentence. The new Node test caught this (see RED below).
  - So `mintShareCode` now reports that case as a `ShareCodeError` too, keeping the original as `cause`.
    `ShareCodeError` is the only error it throws, and both `shareBook` paths can name the cause.
- **`SHARE_CODE_BYTES` is module-private** (polish 2). Nothing imported it. The spec keeps its literal `[16]`, which is
  stricter than comparing against the constant.
- **Node unit tests for `shareBook`'s exact sentence** (polish 4). `cloud-storage.ts` imports cleanly in Node with
  Supabase unconfigured, because `./supabase` binds `null` when the env vars are absent. The tests stub
  `window.localStorage` and `crypto`, and assert the exact `CloudError` on the device path. Each test first asserts
  that `isSupabaseConfigured()` is false, so a configured environment fails loudly instead of testing the wrong path.
  - This differs from the ticket's seam note ("`supabase.ts` … is not imported in Node tests"). Unconfigured, the import
    binds no client and opens no connection.
- **Not changed, as the review says:** Studio still drops the sentence (it belongs to the Studio lane; see Open). The
  375 px well fidelity belongs to T16 (see Fidelity). The `uploadMedia` lint cleanup stays.

## What was built

- **`src/lib/share-code.ts`** (new). It is pure and has no dependencies, so Node tests import it directly.
  - `mintShareCode()` makes 16 bytes from `globalThis.crypto.getRandomValues` and returns 32 lowercase hex characters.
    If `getRandomValues` is missing, it throws `ShareCodeError`. It never falls back to the clock or `Math.random()`.
  - `shareLinkRow(storybookId)` returns `{ storybook_id, share_code }` with a freshly minted code. `createShareLink`
    passes exactly this object to `.insert()`.
  - If `getRandomValues` exists but throws, that is a `ShareCodeError` too, with the original as `cause` (round 1).
    `ShareCodeError` is the only error `mintShareCode` throws.
  - It also exports the `ShareCodeError` class. The byte count, `SHARE_CODE_BYTES = 16`, is module-private.
- **`src/lib/supabase.ts`**
  - `createShareLink` now inserts `shareLinkRow(storybookId)`. A cloud link carries a 32-hex code whatever the column
    default is.
  - `getPublicStorybooks` is deleted. It was a public gallery query that also selected `view_count`, and nothing
    imported it.
  - `getStorybookByShareCode` is unchanged: an exact `.eq("share_code", code)` with no length check. A comment now says
    why that matters.
  - Lint cleanup in the same file: `uploadMedia` no longer destructures an unused `data`. This was a pre-existing
    warning in a file this ticket owns; behaviour is unchanged.
- **`src/lib/cloud-storage.ts`**
  - The private `mintShareCode`, with its `Date.now()`/`Math.random()` fallback, is removed. The module imports the
    shared one.
  - `shareBook` turns a `ShareCodeError` into
    `CloudError("unknown", "Making the link: this browser cannot make a private link safely. Download the .storysync file instead.")`.
    It does this on both the device path and the cloud path, and both catch only `ShareCodeError` (round 1). On the
    cloud path the check runs before `fromSupabase`, so the error is never mislabelled as a network failure.
  - `newId()` tries three things in order: `crypto.randomUUID()`, then `local-<mintShareCode()>`, then a non-secret
    clock/`Math.random` id. Ids are not links, as the ticket allows.
- **`supabase/migrations/002_share_code_128bit.sql`** (new). It contains one statement:
  `ALTER TABLE public.shared_links ALTER COLUMN share_code SET DEFAULT encode(gen_random_bytes(16), 'hex');`.
  - The header comment says three things: the migration is optional for the app, because the app inserts explicit
    codes; existing rows are left as they are; and it is HITL, so Jon applies it to production and agents do not.
  - No existing row is touched.
- **`PRIVACY.md`** rule 4 gets one added sentence: "Cloud links made before share codes became 128-bit used 64-bit
  codes; they keep working until the story is deleted, and every new link is 128-bit." The rest of rule 4 is unchanged.
- **`tests/share-code.spec.ts`** (new). It holds the ticket's seven tests plus six extras; see below.

amber-outlined Copy, and the paper QR card "POINT A PHONE CAMERA HERE" with the reference copy verbatim. Copy changes to

Deviations, and why:

1. **32 hex, not 16 (deliberate, per the ticket).** The reference prints `3f9c2a7be41d0c58` because it shows the honest
   state before this ticket. Ours prints 128-bit codes. T25/T26 should record this as intended, not as a fidelity miss.
2. **The code's tail is clipped inside the well.** The input shows `http://localhost:3000/read?story=5b343d4d99f…` at
   1180 and only `http://localhost:3000/` at 375. The reference's own CSS clips the same way (`.t-url__txt`:
   `white-space: nowrap; overflow: hidden`), and in its ~385 px column a 32-hex URL would be clipped too. The whole URL
   still reaches people in three ways: it is the field's value (focusing the field selects all of it), Copy writes all
   of it (tested), and the QR encodes all of it. The field's styling belongs to `PublishCard.tsx` and T16, which owns
   the s05 two-column rebuild; T02 does not own that file. The reference also drops the scheme, emboldens the code, puts
   Copy inside the well with a lucide Copy icon, and puts a lock glyph on the label. For T16: drop the scheme and
   embolden the code in the display text, and keep the full URL as the field value. The round 1 review confirmed this
   belongs to T16, not T02. `docs/vision/tickets/T16-publish-card-two-column.md` does not mention it yet, and T02 does
   not own that file, so the orchestrator should carry this note into T16.
3. **Environment differences that T02 does not own.**
   - The label meta reads WAV, not AAC/M4A. This Chromium has no AAC encoder, and WAV is the permitted fallback.
   - It reads "LINKED ON THIS DEVICE", not "SHARED UNLISTED", because CI and this checkout have no Supabase.

## Decision log entry

**2026-10-26 · T02 · One share-code minter, 128 bits, never weakened; migration 002 is HITL.**

- **One minter.** Every share link, on the device and in the cloud, is minted by `mintShareCode()` in
  `src/lib/share-code.ts`: 16 bytes from `crypto.getRandomValues`, as 32 lowercase hex characters.
- **No fallback.** Without a CSPRNG, or with one that fails when asked, it throws `ShareCodeError`. `shareBook`
  catches only that error and reports "Making the link: this browser cannot make a private link safely. Download the
  .storysync file instead." A guessable link to a child's voice is worse than no link. Local story ids may still fall
  back to a non-secret value, because ids are not links.
- **Explicit cloud codes.** The cloud insert writes `shareLinkRow(storybookId)`, so links never depend on the column
  default.
- **Old links keep working.** Cloud links made before share codes became 128-bit used 64-bit codes. They resolve by
  exact match, with no length check, until their story is deleted (PRIVACY.md rule 4). The cutoff is this change,
  not a calendar date: until it deploys, new cloud links still take the 64-bit column default.
- **No gallery query.** The unused public query `getPublicStorybooks` is deleted, so `src/` has no query that lists
  other people's stories.
- **Migration 002 is HITL and pending.** `supabase/migrations/002_share_code_128bit.sql` only changes
  `shared_links.share_code`'s default to `encode(gen_random_bytes(16), 'hex')` and changes no row. Jon applies it to
  production; it is optional for the app.
- **Raised, not fixed** (M0-PRD Open Questions):
  - **OQ1, RLS enumeration.** The broad SELECT policies on `shared_links` and `storybooks` still let anyone holding the
    anon key list share codes and published stories. Proposed fix: T02b (migration 003 plus a by-code RPC).
  - **OQ3, counter columns.** `shared_links.views` and `storybooks.view_count` now have no reader or writer in `src/`.
    Dropping them needs Jon's yes.
