I found no High-severity defects in round 1 and two Medium ones. My verdict is **amend**. There were no earlier P6 findings to confirm.

**What holds up:**
- **Codec rule for new recordings.** The recorder now asks for AAC by name first, then WebM, and a plain `audio/mp4` only last. `recordedAsAac` won't call an MP4 AAC if its type or its first 64 KB says Opus (`Opus`/`dOps`). Both publish paths, with and without levelling, now go through that check, so Chromium's Opus-in-MP4 goes through decode and comes out as AAC or WAV. The draft badge checks for Opus first. `tests/a2-codec.spec.ts` pins all of this against a real Chromium recording.
- **Offline deletion.** `sweepDeviceCopy` and `forgetDraftOf` now run before any cloud code is fetched, and `deleteBook` uses the same sweep. The new shelf test refuses the library code and fails on the old flow, as the PR claims.
- **The two test fixes (A14).** The end-card test now waits only for that card's own finite rise animation. The no-network helper skips only same-origin icon loads that no page script started, so no third-party request can hide behind it.

**What needs amending:**
- **P6-R1-01 (Medium, judgement).** Takes published before this fix are never re-checked. Before this head, Chromium 126+ recorded Opus inside MP4 and publish labelled it `audioCodec: "aac"`. At `src/components/studio/Studio.tsx:1297`, any page that already carries a codec label is passed straight through on republish, so the new byte check never sees it. Republishing such a tape publishes Opus again, which breaks the codec rule. Stories already published that way are also untouched. That makes "Fixed in dc85923" in governance.md stronger than what the code does.
- **P6-R1-02 (Medium, judgement).** The new partial-failure branch in `ReadRoom.tsx:709` can show a false message and has no test. With a cloud configured and the library code unreachable, it says "the cloud copy is still on the shelf", even when the tape was only ever on this device. It also skips forgetting the tape's reading positions.
- **P6-R1-03 (Low, judgement).** governance.md and the incident note each describe one red recorded run at `ae62697`. The ledger has two red `phase-run` events at that head, and the second P4-G5 failure (09:51) isn't explained.
- **P6-R1-04 (Low, judgement).** A14 says "No assertion is removed or loosened". The no-network helper now does ignore a class of requests, though narrow and same-origin only, so that sentence should say so.
