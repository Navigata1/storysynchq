Everything below comes from reading the code at `f298c80`. I couldn't run the build, the suite or the budget gate, so none of the size figures were measured by me.

**P4-R1-01 · High · defect: the Player a share link opens is never measured.** `judges/js-budget.json` says the 170 KB budget covers "the Player a share link opens". The gate never loads it: `js_measure.mjs:12` measures only `/`, `/read`, `/studio` and `/protocol`, and `/read` without `?story=` shows only the shelf. The diff then turns the Player into a lazy import (`ReadRoom.tsx:146`), so its code drops out of the one `/read` figure that is measured. The "248 → 161 KB" drop for `/read` is mostly the Player leaving the measurement, not leaving what a grandparent downloads. So the commit title "within the C7 budget on every route" isn't backed for the page the budget is mainly about.
- Fix: add a Player route to the measurement (`/read?demo=1`, or a share-code fixture). Count scripts until the Player's cover is on screen, not until the page's load event. Then either bring that route under 170 KB or narrow the budget's wording by amendment.

**P4-R1-02 · High · defect: the docs and a code comment claim a prefetch the code doesn't do.** `decisions.md` and the comment at `ReadRoom.tsx:143` say "a share link fetches the Player while the tape loads". `next/dynamic` only starts the import when `<Player>` first renders, which is after the tape has loaded. So the two downloads happen one after the other. There's also no loading placeholder, so the screen is blank while the Player downloads, on exactly the slow connections the budget is meant for.
- Fix: share one loader function, call it when the share-link lookup starts (`ReadRoom.tsx:472`), and give `dynamic` a loading placeholder. Or correct the comment and the log entry.

**P4-R1-03 · Medium · defect: one failed load of the cloud code breaks the cloud for the rest of the visit.** `loadSupabase` (`supabase-lazy.ts:24`) keeps the first import's promise forever, including a rejected one. After one network blip, every later save, share, sign-in, shelf read and delete fails until the page is reloaded. That includes the delete that wipes a child's voice from the cloud. The failure also surfaces as a raw chunk-load error, not a `CloudError` with the network kind, so the Studio shows "Your tape could not be saved: Loading chunk … failed" instead of its network sentence.
- Fix: clear the cached promise when the import fails, and wrap `loadSupabase()` failures in `cloud-storage.ts` as a `CloudError` of kind network.

**P4-R1-04 · Low · judgement: the measured build may not match production.** `prod_server.sh` builds without the Supabase env vars, and the clone has only `.env.local.example`, so the measured build most likely has no cloud. In production the cloud is configured, so `/read` asks for the user on mount, which loads the Supabase client (about 55 KB, by the new module's own comment). Whether that lands before the load event depends on timing. Either way, the comment's line that "most visits never touch the cloud" doesn't hold in production.
- Fix: measure with the public cloud variables set to placeholder values, or scope the claim to a build with no cloud configured.
